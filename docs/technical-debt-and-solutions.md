## 1. 통짜 JSON 스냅샷(`state_kv`) ➔ 정규화된 RDBMS 테이블 전환

### 🔴 문제점 (As-Is)
- **현상**: 전교생 명부, 전체 회차, 결제 내역을 하나의 거대한 JSON 문자열(`state_kv`)로 묶어 읽고 씀.
- **부작용**: 데이터가 늘어날수록 네트워크 전송량과 메모리 파싱 부하가 급증하며, 특정 조건 검색(`SQL WHERE/JOIN`)이 불가능함.

### 🟢 해결 솔루션 (To-Be)
1. **정규화 테이블 스키마 설계**:
   - `students`: 학생 기본 인적사항, 담당 교사 ID, 상태(active/ended 등)
   - `sessions`: 회차별 일시, 시간(분), 출결 상태, Meet URL, 과제 완료 여부
   - `payments`: 결제일, 결제금액, 회차 추가 규칙, 결제 수단
2. **무중단 듀얼 라이트(Dual-Write) 마이그레이션**:
   - **Step 1**: 저장 시 기존 `state_kv`와 신규 정규화 테이블에 동시에 기록
   - **Step 2**: 백그라운드에서 과거 데이터 일괄 마이그레이션 스크립트 실행
   - **Step 3**: 읽기(Read) 경로를 신규 테이블로 전환하고 성능 검증 후 `state_kv` 제거

## 2. 수동 Smart Merge ➔ 데이터베이스 트랜잭션 및 낙관적 락(OCC) 도입

### 🔴 문제점 (As-Is)
- **현상**: 두 명 이상의 교사가 동시 수정 시, 클라이언트/서버 애플리케이션 레벨에서 JSON 배열을 비교·짜깁기(`Smart Merge`)함.
- **부작용**: 네트워크 지연이나 레이스 컨디션 발생 시 미묘한 키 누락 및 데이터 유실 위험 잔존.

### 🟢 해결 솔루션 (To-Be)
1. **낙관적 동시성 제어 (Optimistic Concurrency Control)**:
   - 각 데이터 레코드에 `version` (또는 `updated_at`) 컬럼 부여
   - 업데이트 시 `WHERE id = :id AND version = :old_version` 검증
   - 충돌 발생 시(다른 교사가 먼저 수정함) 사용자에게 "최신 데이터로 갱신 후 다시 시도해주세요" 알림
2. **행 수준 락 (Row-Level Locking)**:
   - 교사별로 자신이 담당하는 학생 레코드만 수정하므로, 담당 학생 레코드 단위로만 트랜잭션을 격리해 상호 간섭 원천 차단

## 3. 슈퍼맨 거대 컴포넌트(`StudentHubCore.tsx`) ➔ 도메인 계층 분리

### 🔴 문제점 (As-Is)
- **현상**: `StudentHubCore.tsx`가 학생 목록 렌더링, 시간표 계산, 결제 모달 제어, 동기화 트리거를 한곳에서 모두 처리함 (단일 책임 원칙 위배).
- **부작용**: 코드 수정 시 다른 기능에 미치는 사이드 이펙트 파악이 어렵고 유지보수 비용 급증.

### 🟢 해결 솔루션 (To-Be)
1. **도메인별 커스텀 훅 및 상태 분리**:
   - `useStudentScheduleManager`: 시간표 규칙 생성, 30분 단위 복원 전담
   - `useStudentPaymentFlow`: 결제 모달, 토스페이먼츠 팝업, 회차 추가 전담
   - `useGoogleSyncTrigger`: 구글 캘린더/드라이브 동기화 백그라운드 전담
2. **프레젠테이션 컴포넌트 경량화**:
   - `StudentHubCore`는 조립(Container) 역할만 수행하고, 세부 UI는 독립된 하위 카드 컴포넌트로 분리

## 4. 하드코딩된 관리자 및 인증 이원화 ➔ RBAC 테이블 & 단일 인증 체계

### 🔴 문제점 (As-Is)
- **현상**: 관리자 이메일(`rapah0310@gmail.com`)이 코드에 하드코딩되어 있고, 구글 OAuth 토큰과 Supabase 세션이 브리지 쿠키로 복잡하게 얽혀 있음.
- **부작용**: 타 학원에 SaaS로 공급하거나 멀티 관리자를 둘 수 없으며, 인증 만료 시 복구 동선이 복잡함.

### 🟢 해결 솔루션 (To-Be)
1. **RBAC (역할 기반 접근 제어) 테이블 구축**:
   - `user_roles`: `user_id`, `role ('admin' | 'teacher' | 'student')`, `academy_id`
   - 이메일 하드코딩을 완전히 제거하고 DB 기반으로 동적 권한 부여
2. **Supabase Auth 중심의 단일 파이프라인**:
   - Supabase 내장 OAuth Provider(Google)의 Refresh Token 자동 순환 기능을 적극 활용하여 프론트엔드의 수동 토큰 감시 로직 간소화

## 5. 핵심 계산 로직의 자동화된 단위 테스트(Unit Test) 구축

### 🔴 문제점 (As-Is)
- **현상**: "잔여 수업 비례 환불 공식", "30분 시작 시간표 계산", "수업 시간(90~180분) 복원 알고리즘" 등 민감한 비즈니스 로직을 수동 브라우저 테스트에 의존.
- **부작용**: 로직 리팩토링 시 회귀 버그(Regression) 발생 가능성이 높음.

### 🟢 해결 솔루션 (To-Be)
1. **순수 비즈니스 로직 함수 분리**:
   - UI 종속성이 없는 순수 함수(Pure Function)로 계산 엔진 격리
   - `calculateRefundAmount(totalFee, totalHours, remainingHours, isSameDayCancel)`
   - `resolveRulesForIndex(studentRules, paymentRules, scheduleOverrides)`
2. **Vitest 테스트 스위트 구축**:
   - 정상 케이스뿐만 아니라 경계값(Boundary) 테스트 작성:
     - 수업 당일(12시간 이내) 환불 시 당일 수업 제외 정산 여부 검증
     - 23시 30분 시작 수업의 자정 넘김 시간표 처리
     - 4회차 중 2회차에 시간표가 변경되었을 때의 3, 4회차 종료 시간 계산 일치성
