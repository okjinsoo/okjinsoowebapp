# 인증 보안 개선 우선순위 (2026-03-21)

이 문서는 "지금 당장 무엇부터 고쳐야 안전해지는지"를 빠르게 판단하기 위한 우선순위 표입니다.

기준:
- `P0`: 바로 착수(보안 사고 위험이 큰 항목)
- `P1`: 이번 스프린트 안에 처리
- `P2`: 구조 개선 단계에서 처리

---

## 현재 인증 흐름(아주 짧게)

1. 사용자가 Google 로그인
2. `/auth/callback`에서 토큰을 받아 브라우저 저장소에 세션 저장
3. `/api/auth/bridge`로 브리지 쿠키 동기화
4. 페이지 접근은 `middleware.ts` + `RoleRouteGuard`로 제어
5. API는 `resolveViewerContext`에서 액세스 토큰을 읽어 사용자/권한 판별

---

## P0 (즉시)

### P0-1) 브리지 쿠키 위변조 방지 (서명/검증)

- 배경:
  - 현재 브리지 쿠키(`tutorweb_auth_session_bridge_v1`)는 JSON 문자열 형태입니다.
  - 미들웨어는 이 쿠키를 파싱해 `/a`, `/t`, `/s` 경로 접근 1차 필터에 사용합니다.
- 위험:
  - 클라이언트에서 쿠키 값을 조작할 수 있어, 경로 보호가 우회될 가능성이 있습니다.
- 조치:
  - 브리지 쿠키를 `서명된 값`으로 바꾸고, `middleware.ts`에서 서명 검증 실패 시 즉시 차단
  - 또는 브리지 쿠키를 권한 판단에 쓰지 않고, 미들웨어에서 토큰 기반 서버 검증으로 단순화
- 관련 파일:
  - `app/api/auth/bridge/route.ts`
  - `middleware.ts`

### P0-2) 권한 판별 기준 단일화

- 배경:
  - 미들웨어는 브리지 쿠키(JSON email) 중심
  - API는 `accessToken` 중심
- 위험:
  - "페이지 접근은 통과했는데 API는 401" 같은 불일치가 발생합니다.
- 조치:
  - 권한의 기준을 한 곳으로 통일합니다.
  - 권장: API 기준(`accessToken + Supabase user`)을 표준으로 두고, 미들웨어는 최소한의 리다이렉트 UX만 담당
- 관련 파일:
  - `middleware.ts`
  - `lib/server/supabaseSnapshotApi.ts`
  - `lib/storage/sharedSnapshot.ts`

### P0-3) 브리지 쿠키 최소화 + `httpOnly` 전환 검토

- 배경:
  - 현재 쿠키는 JS에서 읽고 쓰는 구조이며(`document.cookie`), 서버에도 동기화됩니다.
- 위험:
  - XSS가 생기면 쿠키 조작/탈취 표면이 넓어집니다.
- 조치:
  - 브리지 쿠키에 민감 정보 금지(이미 accessToken은 미포함 상태 유지)
  - 가능하면 서버에서만 쓰는 `httpOnly` 세션 쿠키로 전환
  - 클라이언트는 "로그인 상태" 표시만 로컬 상태로 처리
- 관련 파일:
  - `lib/auth/supabaseAuth.ts`
  - `app/api/auth/bridge/route.ts`

## P1 (이번 스프린트)

### P1-1) API 권한표 문서와 실제 코드 동기화

- 배경:
  - `docs/api-auth-matrix.md`에 현재 없는 엔드포인트(`/api/auth/login`, `/api/auth/logout`)가 존재합니다.
- 위험:
  - 운영/개발자가 문서를 보고 잘못 구현할 수 있습니다.
- 조치:
  - 현재 실제 API 기준으로 문서 재작성
  - 각 API별 `401/403` 규칙을 코드와 1:1로 맞춤
- 관련 파일:
  - `docs/api-auth-matrix.md`
  - `app/api/**/route.ts`

### P1-2) 인증/권한 통합 테스트 추가

- 배경:
  - 현재는 유닛 테스트 중심이며 API/권한 흐름 E2E가 거의 없습니다.
- 위험:
  - 리팩터링 시 권한 회귀 버그를 늦게 발견합니다.
- 조치:
  - 최소 시나리오부터 자동화:
    - 비로그인 `/api/snapshot` -> 401
    - 학생 계정으로 타 학생 조회 -> 403
    - 관리자 계정으로 `/api/teachers` -> 200
- 관련 파일(신규 권장):
  - `tests/api/authz/*.test.ts` 또는 e2e 스위트

### P1-3) 보안 로그 표준화

- 배경:
  - 일부 보안 로그는 있으나 형식이 분산되어 있습니다.
- 위험:
  - 장애/침해 조사 시 타임라인 복원이 느려집니다.
- 조치:
  - 공통 필드(`requestId`, `route`, `actor`, `reason`)로 통일
  - 민감 정보(email 전체 등)는 마스킹
- 관련 파일:
  - `middleware.ts`
  - `lib/server/supabaseSnapshotApi.ts`

## P2 (구조 개선)

### P2-1) 인증 전담 모듈 분리

- 목표:
  - 쿠키/토큰 파싱, 사용자 검증, 권한 판정 로직을 공용 모듈로 통합
- 효과:
  - 미들웨어/API/클라이언트 판단 기준 차이를 줄임

### P2-2) Admin 이메일 고정 방식 개선

- 목표:
  - 코드 하드코딩 이메일 대신 운영 테이블 기반 관리
- 효과:
  - 계정 교체/추가 시 배포 없이 운영 가능

### P2-3) CI에서 권한 회귀 검사 자동화

- 목표:
  - PR마다 권한 테스트를 자동 실행
- 효과:
  - "보안 관련 실수"를 머지 전에 차단

## 권장 실행 순서 (짧은 버전)

1. P0-1, P0-2 먼저 처리 (권한 불일치/우회 위험 최소화)
2. P1-1, P1-2로 문서+테스트 정합성 확보
3. P2 구조 개선으로 운영 안정성 강화
